* 0.1 (Q4 2026) (fork of elm-playground's TinyChrome, its own networking)
# unless mentioned otherwise, everything below was done by Claude Code
# (with direction from me)

** networking (its own)
- a body in Brotli or Zstandard is read (Content-Encoding: br, zstd;
  tiny_libs' Brotli, with its dictionary, and Zstd, elm-playground
  after 0.3.3), and asked for: Accept-Encoding: gzip, br, zstd.
  Berkshire Hathaway, which answers in Brotli whatever is asked, loads
- cookies (RFC 6265): a response's Set-Cookie kept (Domain, Path,
  Expires and Max-Age, Secure, HttpOnly), said back in the Cookie
  header of the requests to its site, a redirection's before the next
  request (a sign-in); one jar for the browser, shared by the
  requests on threads (Cookie, Cookie_jar); document.cookie for the
  page's scripts; those with a date kept between runs in the
  profile's Cookies file (Browser_cookies), not with profile=off;
  about:cookies shows the jar. Not done: the Public Suffix List,
  SameSite
- libs/network: elm-playground's networking, the part a browser needs
  (Url, Urlencoded, Http; Asn1, Pem, X509, Tls13; Tcp, Worker,
  Tls_client, Http_client, Http_request), copied to grow here (cookies,
  compression, keep-alive); the cryptography stays tiny_libs'.
  Wrapped (the Playground links tiny_libs' modules of the same names)
  but opened by the libraries using it: the code says Http_request,
  not Network.Http_request
- src/chrome/Fetch: the requests in flight, after the Playground's
  native Commands.ml: http:// by Http_request stepped each frame,
  https:// by Http_client on Worker's threads (threads=off: the frame
  waits); a tab asks for a fetch by a message and never touches a
  socket, the program steps them on each Tick. The Playground no
  longer fetches anything for the browser
- gzip: "Accept-Encoding: gzip" sent, a body with "Content-Encoding:
  gzip" decompressed (Http.parse_response, over tiny_libs' Gzip, in
  elm-playground after 0.3.3): Wikipedia's article on OCaml comes as
  64 KB instead of 354
- tests/network, tests/network_unix: 49 tests (RFC 3986's table, RFC
  8448's TLS 1.3 trace, real certificate chains, a GET over localhost)

** tools
- mini-node: the JavaScript engine in a terminal, as Node.js is V8 in
  one (tools/node: Node_host, MiniNode). A file run as a module, -e a
  text, or a console; console, process (argv, env, exit, stdout),
  timers on the machine's clock and the loop that waits for them,
  require with CommonJS modules (a file run once, in a function that
  gives it exports, require and module), fs (readFileSync,
  writeFileSync, existsSync). Js_eval.eval_in_run and call_in_run: a
  host function called by a script running a text or a function
- mini-curl (tools/curl): a URL fetched and printed by the browser's
  own HTTP, TLS 1.3, gzip and cookies; -i the head, -L a redirection
  followed, -v each request and each answer's head, -d a POST, -o a
  file, -f. Http_client.once: one request, a redirection not followed
- mini-httpd (tools/httpd): a directory's files served on 127.0.0.1
  (-p port): a file's type from its extension, a directory's
  index.html or its listing, 301 to a directory's /, 404, 403 for
  what is above the root, 405 but for GET
- mini-lynx (tools/lynx): a page (an address or a file) as text, its
  links numbered; a number typed follows one, an address opens it, b
  comes back (-dump: no prompt; -w: the width). Line_mode: div,
  section, form, table and a table's row are lines of their own
- tests/tools, an eighth suite: the tools' worked examples, mini-curl
  and mini-lynx on mini-httpd's server forked on a temporary
  directory; Node_host's tests moved there
- docs/sites.md: sixteen sites, from the first web page to BBC News,
  and what each lacks by part (network, HTML, CSS, text, JavaScript),
  in colours; twelve real scripts the same way. 8 sites green, 4
  yellow, 4 red on 2026-10-02 (scripts/sites/dump_sites.sh to check
  again)
- make loc, make loc-v (scripts/stats/loc.py, after elm-playground's):
  the lines of OCaml and how much of the budget they are, 30,000 for
  languages/, libs/ and src/
- scripts/js/Js_survey.exe: real scripts parsed and run, the first
  mistake of each: what the JavaScript engine lacks, most common first

** speed
- libs/opti: Mini_opti.enabled, the switch between an optimized
  function and the simple one kept runnable beside it (after
  elm-playground's Opti); opti=off on the command line, and on
  scripts/perf/Page_bench.exe's. Nothing checks it yet
  (docs/plan_performance.md, step 1)
- a line's shapes built when it is first shown, not the whole page's
  at each relayout (Browser_draw.later, between; opti=off: as before).
  Wikipedia's article on OCaml, 16,000 pixels high: a relayout 450 ms
  to 28, the page first shown in 239 ms instead of 796, its load
  settled in 6.2 s instead of 14.8 (docs/plan_performance.md, step 2)
- a letter drawn as one picture made once (Glyph_picture: its opacity
  from the distance to the pen's strokes) instead of a rectangle a
  segment and a dot a point: a frame of about:chrome drawn in 8 ms
  instead of 74 (Cairo), 32 instead of 116 (software), and a scroll
  far smoother. letters=segments, or opti=off: the pen's way
  (docs/plan_performance.md, step 4b)
- a Wikipedia article scrolled: a step from 340 ms to 15. Cairo's
  platform converted most of the letters' pictures again at each
  frame (it kept the last 32: elm-playground's now keeps them all, up
  to 16 million pixels), and the view read the page's every fragment
  three times a frame to find its players and controls
  (Browser_media.players_of, Browser_draw.controls_of: kept a layout).
  With the pen's segments it was 97, with opti=off 139
- a window at rest is not drawn again: Window_view.view gives back
  the frame before's list of shapes when the model is the same but
  for its time, and the platform skips the frame (run_app
  ~window's skip_same_view, elm-playground after 0.3.3). A frame at rest: 12 ms
  of CPU (about:blank) to 72 (about:chrome) before, 0.3 now; a page
  with a player is still drawn at each (docs/plan_performance.md,
  step 4a)
- scripts/perf: Page_bench.exe (a page's stages timed) and
  load_timeline.sh (the real program's load in time)

** Features
- JavaScript, what libraries need to work and not only load: an
  array's methods on what is only like an array (a jQuery object: a
  copy worked on, written back), Array.from of the same and of what
  can be gone through; new Function (and an async function's
  constructor); with (o) { }; Proxy (get, set, has, deleteProperty,
  apply, ownKeys) and Reflect; a symbol a value of its own (typeof
  "symbol"); a function's name and length; Object.getPrototypeOf of
  what was given no prototype, Object.getOwnPropertyDescriptors.
  jQuery, Underscore, Vue and Alpine work when used: the nine
  libraries of the survey do, and jQuery, Vue and Alpine on one page
  in the browser itself
- the DOM libraries ask for (src/dom): an element's members since the
  first DOM (Script_element: matches, closest, contains, append,
  prepend, before, after, replaceWith, cloneNode, dataset,
  hasAttribute, attributes, compareDocumentPosition, the properties
  that are attributes), comments and fragments, selectors in a tree
  not in the page; events of a script's own (Script_events: new
  Event, new CustomEvent, createEvent, dispatchEvent, click(), once,
  handleEvent; an event bubbles only if it says so); the document as
  a node (Script_document); window's globals (Script_window: the
  classes Node, Element, HTMLElement... for instanceof and their
  prototypes, getComputedStyle, localStorage, MutationObserver,
  matchMedia, history, performance, requestAnimationFrame), window
  the global object. A host object falls through to its prototype.
  JavaScript: a regular expression's source and flags, typed arrays
  (as arrays), an assignment's target read before its value.
  Js_survey uses each library in a page: jQuery, Vue, Alpine and
  htmx now load; htmx, Preact, Mithril and React work
- src/dom: what a page's scripts see (Script_types, Script_dom,
  Script_host, Browser_script), out of src/www: the language in
  languages/javascript, JavaScript in a browser in a directory of its own
- JavaScript: promises (Js_promise: new Promise, then, catch, finally,
  Promise.resolve, reject, all, allSettled, race, any; a thenable
  followed; queueMicrotask) and their jobs, run after each script,
  handler and timer; async functions, arrows and methods, and await
  (ES2017): an async function's body is a coroutine (Js_coroutine: a
  thread asleep but between a resume and its suspend, OCaml 4.14
  having no other stack to set aside). A rejection nobody handles is
  said on the console. A function expression's own name is bound in
  its body. Object.keys leaves out a symbol's key. Alpine parses;
  Vue and Alpine now stop on what the page lacks (Uint8Array,
  MutationObserver)
- JavaScript: classes (a constructor, methods, getters and setters,
  static members, fields, extends with super(...) and super.m(),
  private names read as names) and optional chaining (a?.b, a?.[k],
  a?.(x): the whole chain ends). Js_ast.mli's nodes grouped by the
  edition they came in (ES1, ES3, ES5, ES2015...). [] and [^] in a
  regular expression: nothing, anything. Vue parses
- JavaScript, what libraries look for first (Js_globals): Object's
  defineProperty (a value, or a getter and a setter), entries, values,
  getOwnPropertyNames and the like, Number's and isFinite, Symbol (a
  unique string), Map, Set, WeakMap and WeakSet (in a for-of and a
  spread too), globalThis. An undeclared name assigned to makes a
  global, as scripts not in strict mode rely on. A mistake of the
  engine's own is the script's error, not the program's end. React,
  Underscore and Wikipedia's startup module run to their end
- JavaScript's regular expressions: lookaheads (?=x) (?!x) and
  lookbehinds (?<=x) (?<!x), backreferences \1 and named groups
  (?<name>x) \k<name>, the flags s (the dot takes a newline), u (the
  dot is a whole character; \u{...}) and y. jQuery's and Mithril's
  patterns compile; Mithril runs
- JavaScript, the language since 2015: template literals (their ${ }
  lexed as any expression), destructuring in declarations, parameters,
  for-of and assignments ({ a, b: c = 1, ...rest }, [x, , y]),
  default and rest parameters, spread in arrays, calls and objects,
  an object literal's short forms (a name alone, a method, a computed
  key), getters and setters. Js_eval's properties and operators in
  modules of their own (Js_props, Js_operators). Ten of the twelve
  real scripts now parse (docs/sites.md)
- a field inside an inline-block can be clicked and typed into (Hit:
  the inline-block's room on its line hid what it holds): Google's
  search box. A search there then goes through its consent page (a
  form posted, its cookie kept) and stops: the results ask for
  JavaScript
- JavaScript, the rest of the language of 1999: the comma operator,
  the bits (& | ^ ~ << >> >>> and their assignments), ** and ??, in
  and for (k in o), delete and void, do-while, switch, labels (break
  and continue to one), finally and a catch without a name; a
  conditional's sides may be assignments. Of twelve real scripts
  (scripts/js/Js_survey), jQuery, Mithril, Underscore and Wikipedia's
  now parse, and Preact runs
- a link of several words is underlined whole, the spaces between its
  words too, as browsers draw it: one line a run of words
  (Browser_draw.decorations), where each letter drew its own piece and
  a space had none; a <s>'s line through, the same
- the built-in site is MiniChrome's own: its pages no longer speak as
  the teaching browsers they came from (TinyMosaic, TinyNetscape,
  TinyFirefox), but as pages of the web's ages, each written as its
  time wrote them -- about:mosaic (1993, HTML alone; about:home
  still), about:netscape (1995), about:css (1996), about:firefox
  (pages that are programs) -- and about:history goes on to Chrome
  (JavaScript, CSS, Firefox, Safari); what to try is what this
  browser does (F12, the right click, the zoom); about:chrome links
  them all, says in its header all that the browser is (HTML5's
  parser, CSS, a JavaScript engine, HTTP and TLS, pictures and
  video), and has a JavaScript card: a sentence written by its
  script, tiles made and toggled by clicks
- CSS grid: display: grid, grid-template-columns and -rows (lengths,
  fr, min-content, max-content, auto, minmax(), repeat()),
  grid-template-areas and grid-area (a name, or row / column), the
  shorthand grid-template, the gaps, the other children in the next
  free cell; align-items and align-self down an area; place-content
  (align-content, justify-content). Wikipedia's contents are beside
  its article, not above it, and its article 948 wide; example.com's
  text is in the middle of the window. Css_grid (the values),
  Grid_layout (the arithmetic), Box_grid (the items laid out);
  about:chrome has its card
- everything TinyChrome had in elm-playground 0.3.0: HTML read as
  the WHATWG's tokenizer and tree builder do, CSS's cascade (@media,
  var(), calc(), the attributes' hints) and computed styles, CSS 2.1's
  box model (floats, inline-blocks, positioning, tables, lists) and
  flexbox, SVG pictures, PNG/GIF/JPEG, a small JavaScript (ES5 core)
  and its DOM, <video> and <audio> (MPEG-1 and MP2, MP3, AVI, FLC,
  Y4M, GIF), tabs, the omnibox (an address, or words searched on
  Wikipedia or DuckDuckGo), developer tools (Elements, Network)
- the built-in site: about:chrome, the earlier browsers' pages, and
  about:tube, a video site of our own (its clips in Tube_clips,
  from TinyMediaPlayer's Our_media)
- renamed MiniChrome (the window's title, about:chrome), no longer
  held to TinyChrome's budget of 5,000 lines
- the window resized (dragged, full screen, -size WxH): the page laid
  out again at its width, the chrome placed from the window's edges,
  instead of a 1000 by 1000 picture scaled with black bars (both
  programs, over the Playground's run_app ~screen_follows_window, of
  0.3.1); the window starts at 1280 by 900
- the page zoomed, as in Chrome: Ctrl and + (or =), Ctrl and -, Ctrl
  and the wheel, Ctrl and 0 back to 100%, by Chrome's steps (25% to
  500%); the whole page, laid out at the window's width divided by the
  zoom and drawn scaled; a zoom is its site's (every page and tab of
  that host) and shows in the omnibox
- the page's letters drawn with a round pen (Stroke_text: a dot at
  each point of a stroke): zoomed, the square corners of the segments
  stuck out of every joint, spikes on the bold most of all
- everything drawn at a scale, a browser's device scale factor: the
  desktop's by default (Gui_scale: xrdb's Xft.dpi, 2 where GNOME scales
  a screen of many dots twice -- SDL does not follow it, and the
  omnibox's letters could barely be read), or the one chosen with
  Ctrl+Shift and +, -, 0 or scale=N, kept in the profile; a first
  window is 1280 by 900 of the program's units. A site's zoom multiplies
  it
- a scrollbar at the right of a page longer than the window, over its
  edge (Gui_scrollbar, libs/gui): its thumb dragged, its track clicked
  above or below for a page up or down
- CSS's vh and a media query's height are the window's: the height of
  the part showing the page (less with the panel open), not a constant
  768; the pages laid out again when the panel opens or closes. A page
  exactly as high as that part (a body of min-height: 100vh,
  example.com's) has no scrollbar
- CSS's light-dark(a, b): a, the browser being a light one
  (example.com's grey)
- the command line's words that are not flags are pages to open, a tab
  each: mini-chrome news.ycombinator.com (an address, or words searched)
- libs/gui: Gui_field, the omnibox's text while it is typed into (a
  fresh field replaced, Backspace) and its box
- a right click on the page opens a menu, as Chrome's (Browser_menu):
  on a link, Open link in new tab (behind the tab shown) and Inspect;
  elsewhere Back, Forward, Reload and Inspect (the developer tools on
  the element under the pointer); kept inside the window near its edges
- libs/gui: the pieces of the chrome that know nothing of a browser,
  as values a Model-View-Update program keeps and draws: Gui_menu (a
  menu opened at a point: its place, its shapes, the item under a
  click) and Gui_text (text in cells); Browser_menu says only what the
  menu offers. Then, moved out of MiniChrome.ml, the same pixels:
  Gui_tabs (the strip of tabs), Gui_toolbar (Back, Forward, Reload,
  Stop), the status bubble (Gui_text), the colours (Gui_kit)
- src/window: MiniChrome.ml (875 lines) split by concern, the same
  pixels (24 frames compared): Window_model (the state and messages),
  Window_layout (the model read: the geometry, the pointer),
  Window_tabs (the model changed: tabs, scroll, zoom, the profile),
  Window_update, Window_view; src/main's MiniChrome.ml is the main
- src/layout: Box_layout.ml (1,268 lines) split by concern, the same
  pixels (52 frames of the built-in pages compared): Box_types (the
  box, a line's items, a block being laid out), Box_tree (a box read),
  Box_inline (words on lines beside floats), Box_flow (a block's width,
  margins and content), and Box_layout, the recursion (680 lines)
- src/www: Browser_script.ml (724 lines) split by concern, the same
  pixels and tests: Script_types, Script_dom (the page's mutable copy),
  Script_host (the host objects: an element's, document, location),
  and Browser_script, the tasks (scripts, events, timers)
- docs/architecture.md: the Model-View-Update loop, the pieces of
  libs/gui and their style among the four of elm-playground's
  notes_gui.md, the one process and its pool of four threads next to
  Chrome's processes, the capabilities, what is kept between runs
- the profile (Browser_profile), what is kept from one run to the
  next: ~/.config/mini-chrome/Preferences, JSON as Chrome's, for now
  the window's size (it opens as it was left) and each site's zoom,
  written a second after one changes and when the program ends; profile=DIR for another directory, profile=off for
  none; a file that is not JSON is reported and left alone.
  The first files the program reads and writes, by Cap.open_in and
  Cap.open_out (and Cap.env for the directory) handed down from
  Cap.main, as Cap.network is for sockets
- -v (or -verbose): each file and URL opened said on the terminal, by
  Logs.info -- the profile's file read and written, the TLS roots'
  file, each request (GET or POST) and its answer (status, bytes, a
  redirection), a built-in page; -debug and -quiet as well (the
  Playground's flags, the names of xix's programs)
- languages/json: JSON read (elm-playground's Json, over our
  JavaScript lexer: comments and a last comma taken) and written

** Bug fixes
- the wheel scrolled the wrong way
- a q typed anywhere (the omnibox, a page's field) quit the browser:
  the Playground's key, on every native program. Fixed in
  elm-playground after 0.3.1, where the platform's keys are Ctrl + a
  key: Ctrl+Q quits here too (nothing changed in this repository; with
  0.3.1 installed, q still quits)
- the program ended (Cairo's INVALID_MATRIX) on a picture drawn with no
  width or no height: Hacker News' comment pages, which indent with
  <img src="s.gif" width=0>; a player squeezed to nothing

** build infra
- one opam package, mini-chrome, standing on elm-playground's packages
  (0.3.1): the Playground for its window and drawing
  (elm_playground, elm_playground_native: SDL and Cairo), tiny_libs for
  the pictures, sound and video decoders
- ./configure (after elm-playground's): checks for SDL2 and Cairo,
  finds elm-playground's packages (from opam, or a 'make install' in an
  elm-playground checkout, or else pinned from the 0.3.1 tag)
- no Cairo needed: two programs, mini-chrome (Cairo's platform when
  installed, else the Playground's own rasterizer, by dune's select)
  and mini-chrome-software (always the rasterizer); ./configure
  --software leaves Cairo out, as it does by itself without Cairo
- bin/ symlink to _build/install/default/bin: ./bin/mini-chrome
