Debugging a page that looks wrong
================================

This file is about the *technique*, not the specific bugs (see git log
and the comments in the source for those). Kept so the
approach can be reused the next time a page does not look as it does
in Chrome. A session adds a section; the first is below.


Session 1 (2026-10-01): "a missing <h1> on example.com"
--------------------------------------------------------

docs/history.md listed it as the first bug to fix. It was not one: the
page has no <h1>. What follows is how that was found in four commands,
and what the page showed instead.

1. Read the bytes before the code
---------------------------------
What is missing on the screen may be missing in the page. Before
opening Html_tree or Box_layout:

  curl -s https://example.com
  curl -s https://example.com | grep -c '<h1'      # 0

example.com was rewritten (Last-Modified: 28 Sep 2026, from `curl -s
-D- -o /dev/null`): its <body> is now a <p>, an <a> and a <script
src=/s.js>, with "Example Domain" only in the <title>. The heading
"missing" was the one remembered from the page of the years before.

Then check that the browser got the same bytes, with -v:

  ./bin/mini-chrome -v ... url=https://example.com
  mini-chrome: [INFO] 200 https://example.com (713 bytes)

and `curl -s https://example.com | wc -c` says 713 too. A server may
answer another page to another User-Agent (ours is "elm_playground"):
`curl -A elm_playground` rules that out.

2. See the page without a screen
--------------------------------
  SDL_VIDEODRIVER=dummy SDL_AUDIODRIVER=dummy \
    ./bin/mini-chrome -size 1400x800 -dump-frame 120 /tmp/page.png \
    url=https://example.com profile=off

then Read the PNG. Two things to know:

- The frame's number must be late enough for the answer to be there.
  CLAUDE.md's example dumps frame 5 of about:tube, a built-in page; an
  https:// page fetched on a Worker thread is not there at frame 5, and
  the dump is a blank page that looks like a bug. 120 was enough here;
  -v shows whether the "200" line came before "quitting".
- Wrap it in `timeout 60`: a -dump-frame that never comes (a typo in
  the flags) leaves a program running with no window to close.

3. Try the suspected page from localhost
----------------------------------------
To know whether an <h1> is drawn at all, give the browser the page
that had one. http:// to localhost needs no TLS and no Internet:

  mkdir /tmp/www && cat > /tmp/www/old.html     # the page, pasted
  (cd /tmp/www && python3 -m http.server 8765 &)
  ./bin/mini-chrome ... -dump-frame 60 /tmp/old.png \
    url=http://localhost:8765/old.html profile=off
  pkill -f 'http.server 8765'

The older example.com (a <div> with an <h1>, a <p> and a link) drew
its heading, bold and larger. So: the tree builder, the cascade and
the layout were never at fault. The same trick cuts a large page down:
save it, delete half, look again.

4. Then compare with Chrome, rule by rule
-----------------------------------------
With the bytes known, read the page's own <style> and ask of each
declaration whether we honour it. On example.com's one rule that gave
the real differences, none of them about a heading:

- `background: light-dark(#eee, #222)`: the function was not known, the
  declaration dropped, the page white instead of grey. Fixed
  (Css_values.color).
- `min-height: 100vh`: a scrollbar on a page of five lines. The
  viewport's height was the constant 768 (Browser_page.viewport_height),
  not the window's, so 100vh was taller than the page's part of a window
  800 high. Fixed (the settings' height); and then a second cause
  showed, hidden by the first: a page exactly as high as its area still
  scrolled by a line, its lines rounded up and the area's down
  (Browser_tab.line_count).
- `display: grid; place-content: center`: laid out as a block, so the
  text is not centred down the window (the grid of history.md's list).
- `<script src=/s.js>`: not run (the host is not in default_allowed),
  and it is ES2015 (arrows, a spread, a /u regexp) for an ES5 engine.
  In Chrome it adds a picture above the text and five translations.

A dump with a scrollbar where Chrome has none, or a background of the
wrong colour, is worth the question "which declaration?" before "which
module?".

Lessons
-------
- A bug in a list is a claim: reproduce it, and read the page's
  source, before reading ours.
- Real sites change. A check against one (history.md's "example.com
  rendered pixel for pixel") is true of the day it was made; a page
  that must stay the same belongs in data/ or in a test's string.


Session 2 (2026-10-01): "a Wikipedia article is slow"
------------------------------------------------------

docs/history.md said the layout was slow, and proposed to measure
first. The network was suspected too (a TLS handshake per request).
Neither was it: the page's shapes are. No profiler was at hand (no
perf; ptrace_scope 1, so no gdb on a running program), and three
cheap measures were enough.

1. real against user: is it waiting, or computing?
--------------------------------------------------
  time ./bin/mini-chrome -dump-frame 400 /tmp/t.png url=... profile=off

  real 27.2 s   user 26.5 s

A program waiting for the network has a user time far under its real
time. Here they are the same: one core is busy from the first frame to
the last, and no faster network (gzip, keep-alive) would change much.

2. A time on each line of -v
----------------------------
-v says each request and each answer. A time before each line (a
filter of five lines of Python on stderr: time.time() - t0, then the
line; scripts/perf/load_timeline.sh, kept) shows the shape of the
load:

   0.04 GET  the page
   0.71 200  the page                     (the network: 0.7 s)
   1.56 GET  two sheets, four pictures    (read and laid out: 0.85 s)
   2.18 200  ...
   3.26 200  ... (four answers at once)
   5.90 200  ...
   7.19 200  ... (four at once)
   ...
  14.82 200  the last
  27.10 quitting                          (frame 400)

The answers come in bursts one to 2.6 s apart. Fetch.step hands the
answers at each Tick, so a burst is a frame, and a frame of 2 s is a
page laid out again once per answer in it: four answers, four times.

And the frames after the last answer: 600 frames take 33.6 s, 1200
take 51.8, so 30 ms of CPU a frame for a page nobody touches.

3. A harness that times the stages
----------------------------------
An executable linking the libraries (scripts/perf/Page_bench.ml, kept:
Http_client.get for the page and its sheets, then each stage between
two Unix.gettimeofday), on the same page:

  Charset, Html_lexer, Html_tree           12 + 33 + 28 ms
  Computed.styles (cascade, computed)     290 ms
  Box_layout.layout                        33 ms
  Browser_boxes.draw                      557 ms
  Browser_page.laid_out, styles memoized  520 ms
  the page over TLS, gzip                 457 ms (1246 the first time)

The layout is 33 ms. A relayout is 520 ms because of what follows it:
the shapes of every letter of a page 16,000 pixels high, a rectangle
for each segment of each stroke and a dot at each point (the round
pen), built though 713 pixels show. 24 answers, 24 times.

To time a stage that the module does not export (the cascade inside
lay_out), time the whole twice: once with a memo missed, once with it
hit; or rebuild its input with what is exported (Css_syntax.
parse_stylesheet and Computed.styles here).

Lessons
-------
- real = user: do not optimize the network.
- A name in a list of things to do ("the layout is slow") is a guess
  until each stage has its number: the layout was 6% of a relayout.
- Count how many times, not only how long: 0.5 s is slow, 24 times
  0.5 s is the 14 s.

What to do about it is docs/plans/plan_performance.md. Its step 2 (the
shapes built when a line is shown) took a relayout from 450 ms to 28,
and the same two tools measured it, with opti=off for the "before" on
the same machine and the same day.


Session 3 (2026-10-02): "scrolling the Wikipedia article is sluggish"
----------------------------------------------------------------------

The letters had just become pictures, about:chrome scrolled smoothly
(a frame drawn in 8 ms instead of 74), and the article did not.

1. A script of the same gesture, against the same run at rest
-------------------------------------------------------------
-script presses keys at frames. 600 presses of the arrows after the
load ("down:500,down:502,...", then as many "up"), and the same run
without them, to the same frame: the difference of their CPU times
(/usr/bin/time's %U), divided by 600, is a scroll step. A page at
rest costs nothing now (the view's same list is not drawn), so the
difference is the steps alone.

With 150 presses the answer moved by 10 ms from one run to the next:
the load itself, with its TLS on threads, takes 5 to 7 s of CPU, and
that noise was divided by 150 only. With 600 it is steady to half a
millisecond. And a word added to the command line to label a run was
opened as a page: a third number that meant nothing. The two runs
must differ by the script alone.

2. The same measure on the other platform
-----------------------------------------
  Cairo:     pictures 340 ms a step, the pen's segments 145
  software:  pictures  52,           the pen's segments 197

Pictures slower than segments on one platform and four times faster
on the other: the fault is that platform's way with pictures, not
the pictures. Cairo's kept the last 32 it converted, and an article's
line has more different letters than that.

3. A clock round each part, in the real program, then taken out
---------------------------------------------------------------
The drawing alone was 7 ms (-uncapped at the scrolled place: every
frame drawn, the view the same list) and a step 26: 19 ms were not
the drawing. Page_bench had each suspect at 1.5 ms. So a table of
(count, total time) by name, a `timed "name" (fun () -> ...)` round
update by message, round view, and round four parts of the view,
printed at exit: Browser_media.draw 9.4 ms, controls_drawn 3.4,
animated 2.5 -- three readings of the page's 12,000 fragments, a
frame, for a page with no player. In the program they cost three
times what the bench said (the collector, with the rest of a frame's
work around). The clock was a throwaway: the files put back from
their copies, the numbers kept here.

Lessons
-------
- "Fast all the same" is a thing not understood: the cache of 32 was
  noted the day before as odd and left, because about:chrome was fast.
- A bench of one stage alone can be three times off the program's.
- Make the measure long enough that the run's own noise is small in
  it, and change one thing between two runs.


Session 4 (2026-10-03): "a program compiled to JavaScript runs at one frame a second"
---------------------------------------------------------------------------------------

The Playground's menu (tinybox: OCaml compiled by js_of_ocaml, 538 KB
of JavaScript) took 6.8 s to start in our engine and 870 ms a frame.
The plan (docs/plans/plan_tinybox.md) had a guess, read in the code:
the scopes' tables. Session 2 had no profiler; this time one was
looked for first, and there was one.

1. A profiler that needs nothing: valgrind's callgrind
-------------------------------------------------------
`which perf valgrind gprof`: perf was not installed, valgrind was.
callgrind runs the program on a simulated processor and counts the
instructions of each function. No flag at compile time, no root; the
price is a program fifty times slower, so what is run under it is
small.

  valgrind --tool=callgrind --callgrind-out-file=/tmp/cg.out \
    ./_build/default/tools/node/MiniNode.exe loop.js
  callgrind_annotate /tmp/cg.out | head -50

(loop.js: 100,000 calls of a function of two arguments, a line of
JavaScript; half a minute under valgrind.) The answer, the functions
by the instructions they ran themselves:

  195,918,918 (11.47%)  runtime/hash.c:caml_hash
  147,101,995 ( 8.61%)  stdlib/hashtbl.ml:camlStdlib__Hashtbl__key_index
  112,117,652 ( 6.56%)  runtime/memory.c:caml_page_table_lookup
  109,372,576 ( 6.40%)  runtime/compare.c:do_compare_val
   99,280,699 ( 5.81%)  runtime/hash.c:caml_hash_mix_string
   62,427,434 ( 3.65%)  runtime/array.c:caml_make_vect
   60,772,465 ( 3.56%)  camlJs_eval__eval_expr

How to read it:
- The total divided by what the program did is the number to keep:
  1,708 million instructions for 100,000 calls is 17,000 a call. It
  does not move from a run to the next (a count, not a clock), so a
  change of 2% shows, where a time needs a long run to show 10%.
- The OCaml runtime's names say what the OCaml code asked: caml_hash
  and Hashtbl's key_index are a table looked into; do_compare_val and
  caml_page_table_lookup are the comparison of any two values (=,
  compare, List.assoc, a Hashtbl's keys) where the types were known;
  caml_make_vect is Array.make (here Hashtbl.create's); caml_alloc_string
  with printf below it is a number written as text. Two thirds of
  this profile were names hashed and tables made.
- A name ending in '2 is the function called from itself (the
  evaluator is recursive): add the two lines.
- camlJs_eval__fun_3514 is a function with no name: a closure, or
  the body the compiler made of a function with an optional
  argument. `objdump -d prog | awk '/<camlJs_eval__fun_3514>:/,/ret/'`
  and the calls it makes (bl ...tick, bl ...eval_expr) said which.
- --inclusive=yes (a function with what it calls) gives nonsense on
  a recursive program: millions of percents. Keep to the exclusive
  list.

2. The small program first, then the real one
----------------------------------------------
The loop's profile gave the first fix (the scopes); the real program
then showed what no small loop had: a[1] writing 1 as a string to
read it back as a number (printf in the profile of a program that
prints nothing), and an object's keys compared as any two values. A
bench was written to run the real one with no window
(scripts/perf/Js_bench.exe page.html 3 loops=off: three minutes under
callgrind), and run again after each change. When the list became
flat -- the evaluator itself first at 10%, nothing of the runtime's
above 4% -- there was no more to take that way: four times faster,
and the next factor is another design, not another fix.

3. Two runs of one program to find a wrong answer
--------------------------------------------------
The menu drew, the arrows moved its selection, and a click or the key
"a" did nothing. Suspected: the engine wrong on something js_of_ocaml's
runtime does (its comparison of two values). A bundle of 538 KB with
its names shortened cannot be read; but OCaml can be compiled to
JavaScript here, and Node is the reference:

  ocamlfind ocamlc -package js_of_ocaml -linkpkg t.ml -o t.byte
  js_of_ocaml t.byte -o t.js
  node t.js > node.out; ./bin/mini-node t.js > mini.out
  diff node.out mini.out

t.ml: fourteen lines of Printf over =, compare, Hashtbl, String, List,
Int64, floats. The first diff was the bug's kind (a typed array's
subarray missing); with it the outputs were the same, so the engine's
arithmetic was not at fault -- a suspect cleared in ten minutes. A
program of this kind is the cheapest test of the engine against a
real compiler's output.

4. The first error, each time
------------------------------
What was wrong was said on the console all along (-v): "ba.data.subarray
is not a function", then, that one fixed, "d.getContext is not a
function". The second was thrown inside the function
requestAnimationFrame calls, before it asks for the next frame: the
animation stopped there, and every key after it "did nothing". Three
runs had been spent on the keys and the mouse (a page of a few lines
that logs each event it is given: they were right) before the line
on the console was read as the cause and not as a side matter.

A Proxy round an event (new Proxy(e, { get(t, k) { seen.push(k);
return t[k] } }), given to window.dispatchEvent) says which of its
fields a program reads: the way to know what an event must carry
without reading the program.

Lessons
-------
- Look for the profiler before deciding there is none: `which
  valgrind`.
- Instructions counted are steadier than seconds; divide them by what
  the program did.
- An uncaught error in a callback that re-arms itself (an animation
  frame, a timer set again at its end) stops everything after it:
  read the console before the events.
- When a big program gives a wrong answer, make a small one with the
  same compiler and compare with another engine.

Session 5 (2026-10-04): "an application whole in JavaScript: 9fans, then Discourse"
------------------------------------------------------------------------------------
Two sites that are a page of a few kilobytes and megabytes of scripts
(9fans.topicbox.com: one framework, 600 KB; discuss.ocaml.org: Ember,
4 MB of modules). Each stops on its first error, and the error is in
one line of a megabyte. What follows is how each was found without the
window, and without the site.

1. The site saved once, then run with no network
-------------------------------------------------
scripts/js/Page_scripts.exe runs a saved page's scripts with no
window. With FILES=DIR, a request whose path is a file under DIR is
answered with it (a <script src> too, and with
Access-Control-Allow-Origin: * as a CDN says); a POST by the md5 of
its address and body, under DIR/_post/. A loop of ten lines of Python
fills DIR: run, read the "request: GET ..." lines with no "(saved",
fetch those with curl, run again, until none is missing
(/tmp/.../disc/fetch.py; record.py did the POSTs for 9fans).

  curl -A "<a browser's User-Agent>" -o page.html https://discuss.ocaml.org/
  FILES=$PWD Page_scripts.exe page.html https://discuss.ocaml.org/

Why: a run is then the same each time, takes seconds, and nothing is
said to the site while it fails (9fans reports its errors to a
tracker: a browser being debugged should not fill it). And the saved
bundle can be edited (below).

A third argument is an expression asked at the end; a fourth, another
asked three seconds of the page later: a click, then what it made --

  Page_scripts.exe local.html URL \
    "document.getElementById('sidebar:latest').querySelector('a').click()" \
    "location.href + ' | ' + document.querySelectorAll('.v-GroupItem').length"

To see the page it built: ask document.documentElement.outerHTML, take
the scripts out, put the sheets in <style>, serve it with mini-httpd
and dump it. The layout is then looked at with no script running.

2. A syntax error in a line of a megabyte
------------------------------------------
"expected ';' or a new line, not 'yt' (line 48)" says nothing when
line 48 is 62 KB. JS_SYNTAX=1 adds the twelve tokens before the one
refused:

  ..., after: '(' 'e' ')' '{' 'let' '{' 'default' ':' 'n' '}' '=' 'await'

then grep -o '.\{120\}(e){let{default:n}=await yt' in the bundle shows
the source: "async#n(e){" -- a private method right after a word,
which the lexer read as one name. Three of Discourse's stops were
found so (a regular expression after an if's ")", async#n, async *m in
an object).

3. An error with no place: the calls it leaves by
--------------------------------------------------
"Cannot read properties of undefined (reading 'call')" in 4 MB. With
JS_STACK set to words of the message, the engine prints the functions
the error leaves by, the innermost first (forty at most; WALK=1, the
evaluator, whose calls are the ones counted):

  WALK=1 JS_STACK="reading 'call'" FILES=$PWD Page_scripts.exe page.html URL
  thrown: Cannot read properties of undefined (reading 'call')
    left _set, written at line 4
    left set, written at line 4
    left xo, written at line 4
    left create, written at line 4 ...

(JS_STACK=1 alone is the older use: the stack when it overflows.) The
names are then grepped in the bundles.

3b. An application that fails quietly: the first values thrown
---------------------------------------------------------------
GitHub's page was emptied by React with one line on the console, its
error 321 ("invalid hook call"), which was not the fault: a framework
catches most of what is thrown, and reports the last thing, not the
first. JS_THROWS=n prints the first n values thrown, caught or not,
each with the calls it leaves by:

  JS_THROWS=8 WALK=1 FILES=$PWD Page_scripts.exe page.html URL

The first was a SyntaxError of ours, "Invalid assignment target",
thrown from a module React loaded lazily and whose failure it took for
a component to try again; the 321 came from React calling components
outside a render to learn their stacks (it catches that one itself).
To read before believing a framework's own message.

4. A line of console.log put in the saved bundle
-------------------------------------------------
The stack said where, not which property. The bundle being a file of
ours, a line is added to it (a copy kept beside):

  s.replace("_set(e,t,n,r){let i=", "_set(e,t,n,r){if(!this._setter)console.log('NOSETTER',t,...);let i=")

"NOSETTER isReadOnly" -- and grep isReadOnly showed a getter, a static
block decorating it, then its setter: our classes ran the block before
the setter was defined. What a debugger's breakpoint would have said,
with sed.

5. The small program, again
----------------------------
Each time the cause was guessed, ten lines of plain JavaScript were
written to show it, run by mini-node and by node, the outputs
compared: super in a static method, getPrototypeOf of a Proxy, an
accessor's descriptor, "a".toString(). The framework is then out of
the picture, the fix has its test, and what else is wrong in the same
corner shows in the same run (true.toString() beside "a".toString()).

6. A browser that hangs: its stack, from outside
-------------------------------------------------
The window froze once the pointer was on 9fans' page. Reproduced with
no hand: -script "at(90;255):400-460,click:420" moves the pointer and
clicks at given frames. timeout(1) did not end it (use timeout -s
KILL). The stack, by gdb started with the program and interrupted:

  (gdb -q -batch -ex run -ex "bt 45" --args ./_build/default/src/main/MiniChrome.exe ... > gdb.txt 2>&1 &)
  sleep 70; pkill -INT -f "MiniChrome.exe -size"

(gdb -p on a running process is not allowed here: ptrace.) "bt 45" is
the innermost frames, "bt -60" the outermost: the first said
Js_value's display in a recursion of hundreds of frames, the second
who asked -- Js_eval.ml:694, the message of "x is not a function",
printing an application's every object. Two bugs: the listener was an
object with handleEvent on its class, and a value was shown without
bound.

Careful with pkill -f: a pattern that is also in the command line of
the shell running it kills that shell.

7. A click that does nothing: say what was hit
-----------------------------------------------
One Logs.info for a day in Window_update.click_page: the element
under the pointer, and whether the page prevented the default. "click
at 90, 169: <div id=v13 class=v-App>" -- not the link: the hit test
took the first box at the point, the one underneath. Taken out after.

8. Where a load's seconds go
-----------------------------
discuss.ocaml.org took 29 s. scripts/perf/load_timeline.sh: the
sheets' answers spread over 12 s, then the pictures' over 15, and
"CPU 26 s" of 43 -- computing, not waiting. Page_bench.exe on the
same page: Computed.styles 690 ms (1.2 MB of CSS), a layout with the
styles kept 16 ms. So 31 sheets, each laid out as it came: 12 s; and
the pictures were not layout: mini-curl on one, 0.2 s of user time --
a TLS handshake each, 120 of them, one thread at a time. Laid out
once when the sheets are all there, connections kept (Keep_alive), six
threads: 7.5 s.

Lessons
-------
- Save the site and run it offline: the same run each time, in
  seconds, and nothing sent to the site's error tracker.
- Make the error say more before reading the bundle: the tokens
  before a syntax error, the calls an error leaves by.
- The saved bundle is a file: put a console.log in it.
- Each cause guessed becomes ten lines run by node and by mini-node.
- A hang has a stack: gdb from the start, interrupted; the innermost
  frames say what loops, the outermost who asked.
- An error message must not print a value whole.

Session 5, continued: an undefined value, followed back; then the time
------------------------------------------------------------------------

9. A watchpoint on a script's variable
---------------------------------------
"A closure's variable is an object when it is made, undefined when it
runs": that looked like the engine losing a captured variable.
__watch(() => 0, "t"), a line put in the saved bundle where the
closure is made, watches the binding of t that closure sees; the
engine says "watch: t changed to ..., seen entering f of chunk.js" at
the first call entered or left after a change (Js_eval.watch_check).
It said nothing: the variable never changed. The instance that failed
was simply another one than the one logged -- an id given to each
(globalThis.__n = (globalThis.__n || 0) + 1) showed it was undefined
from the start. A suspected engine bug cleared in two runs; SIMPLE=1
(Page_scripts: the simple scopes) had said the same.

10. Following a wrong value back, an opcode at a time
------------------------------------------------------
The undefined came out of a stack machine (Glimmer's). A script of
patches kept beside the bundles (inst.py: each a console.log put
before one line, "inst.py off" to take them out) says, for every
push of undefined, the opcode running (a global set in the
dispatcher). Each run moved one step back: the opcode that read a
variable, the one that bound it, the arguments it bound from, where
those were merged, what was merged -- Object.assign({}, x), whose
result had the keys and no value. Six runs, each a minute.

To number every closure of a file without changing what it does:
"()=>" replaced by "(__z=(globalThis.__w=N))=>" -- a default
parameter is evaluated at each call, and works for both kinds of
body.

11. A profile by hand: gdb, interrupted every second
-----------------------------------------------------
callgrind makes a run fifty times longer: half an hour for one of
thirty seconds. gdb's batch mode, a "bt 8" and a "continue" twenty
times over, and a loop that sends SIGINT to the program each second:

  (gdb -q -batch -x samp.gdb --args Page_scripts.exe ... > samp.txt 2>&1 &)
  for i in $(seq 24); do kill -INT $(pgrep -x Page_scripts.ex); sleep 1.2; done
  grep "^#[0-3] " samp.txt | ... | sort | uniq -c | sort -rn

(pgrep -x takes the name's first fifteen letters; pgrep -f would find
gdb itself.) Twelve samples were enough: nine in List's "@" and in
List.exists under Js_globals' put -- a Map kept as a list. Hashed: 56
s to 34. The same on the browser itself (thread 1's stack) said the
cascade ran again at each change of the tree; callgrind on
Page_bench.exe then said where in it: List.remove_assoc, 41%.

12. A real browser's picture beside ours
-----------------------------------------
Chrome is on this machine, and draws a page to a file with no window:

  google-chrome --headless=new --disable-gpu --no-sandbox --hide-scrollbars \
    --window-size=1400,814 --virtual-time-budget=15000 --screenshot=ref.png URL

(814: our window of 900 less the 86 of its chrome, so the two pages
have the same height.) The two pictures side by side said what was
missing on Discourse in one look -- the icons, the lines between rows,
the categories' squares, the tab's line -- where reading its 1.9 MB of
CSS would not have.

13. A page an application built, kept as a file
------------------------------------------------
Each look at the layout cost the forty seconds of the application's
start. Page_scripts.exe page.html URL "document.documentElement.outerHTML"
gives the document it built; the scripts and <noscript>s taken out, a
<base href> put in, it is a static page (dstatic.html) that
mini-httpd serves and the browser lays out in two seconds, its sheets
fetched as usual. Six rounds of layout work were done on it; and

14. A profile after each fix, not one profile
----------------------------------------------
callgrind on the same run three times (thirty minutes each, in the
background while other work went on): 127 G instructions, then 65 G.
Each profile's top lines were plain wastes that hid the next ones --
List.assoc_opt and List.mem under Dtd (an element's origin, asked for
every node of every freeze: a third of the run), the lexer's
String.sub. callgrind_annotate --tree=caller, read by a few lines of

blame; "caml_c_call" among the callers means a polymorphic compare.

15. A loaded machine: least of several, or instructions
--------------------------------------------------------
With other builds running (uptime: load average 30) the same run took
15 s, then 37: /usr/bin/time's "user" is no better than the clock
when the cores are shared. Two ways out: the least of three or four
runs of each variant, taken in turns (what the machine can do when
left alone); or callgrind's instructions, which do not depend on the
load, in the background.

16. Which task is long
-----------------------
Page_scripts.exe with TIMES=1 says what each task took (the first run,
each turn of timers, each batch of answers), when it is over 0.2 s:
Discourse's start was one task of twelve seconds, a single promise
job of ten in it -- so no cut between tasks or jobs could show
progress, and the run itself had to give way (Js_slice).

17. Trying an optimization: count, and put it back if it did not pay
---------------------------------------------------------------------
A small script per question (props.js: method calls on a class of
thirty methods; calls.js: calls, a method, an arrow, an object made),
run under callgrind: "I refs" before and after, to the instruction,
whatever the machine's load.

  valgrind --tool=callgrind --callgrind-out-file=cg.out mini-node props.js 2>&1 | grep refs

The property table: 4.99 G to 3.50 G, kept. Keys compared by their
length and first letter before String.equal: 3.007 G to 3.038 G --
worse, put back. Js_bench.exe read=FILE times a script's reading by
stage (lexing, parsing, Js_quicken) with the megabytes each makes:
it said reading was 0.7 s of a 13 s start, where a guess from an
inclusive profile had said a quarter.
