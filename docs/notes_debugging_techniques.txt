Debugging a page that looks wrong
================================

This file is about the *technique*, not the specific bugs (see git log
and the comments in the source for those). Kept so the
approach can be reused the next time a page does not look as it does
in Chrome. A session adds a section; the first is below.


Session 1 (2026-10-01): "a missing <h1> on example.com"
--------------------------------------------------------

docs/history.md listed it as the first bug to fix. It was not one: the
page has no <h1>. What follows is how that was found in four commands,
and what the page showed instead.

1. Read the bytes before the code
---------------------------------
What is missing on the screen may be missing in the page. Before
opening Html_tree or Box_layout:

  curl -s https://example.com
  curl -s https://example.com | grep -c '<h1'      # 0

example.com was rewritten (Last-Modified: 28 Sep 2026, from `curl -s
-D- -o /dev/null`): its <body> is now a <p>, an <a> and a <script
src=/s.js>, with "Example Domain" only in the <title>. The heading
"missing" was the one remembered from the page of the years before.

Then check that the browser got the same bytes, with -v:

  ./bin/mini-chrome -v ... url=https://example.com
  mini-chrome: [INFO] 200 https://example.com (713 bytes)

and `curl -s https://example.com | wc -c` says 713 too. A server may
answer another page to another User-Agent (ours is "elm_playground"):
`curl -A elm_playground` rules that out.

2. See the page without a screen
--------------------------------
  SDL_VIDEODRIVER=dummy SDL_AUDIODRIVER=dummy \
    ./bin/mini-chrome -size 1400x800 -dump-frame 120 /tmp/page.png \
    url=https://example.com profile=off

then Read the PNG. Two things to know:

- The frame's number must be late enough for the answer to be there.
  CLAUDE.md's example dumps frame 5 of about:tube, a built-in page; an
  https:// page fetched on a Worker thread is not there at frame 5, and
  the dump is a blank page that looks like a bug. 120 was enough here;
  -v shows whether the "200" line came before "quitting".
- Wrap it in `timeout 60`: a -dump-frame that never comes (a typo in
  the flags) leaves a program running with no window to close.

3. Try the suspected page from localhost
----------------------------------------
To know whether an <h1> is drawn at all, give the browser the page
that had one. http:// to localhost needs no TLS and no Internet:

  mkdir /tmp/www && cat > /tmp/www/old.html     # the page, pasted
  (cd /tmp/www && python3 -m http.server 8765 &)
  ./bin/mini-chrome ... -dump-frame 60 /tmp/old.png \
    url=http://localhost:8765/old.html profile=off
  pkill -f 'http.server 8765'

The older example.com (a <div> with an <h1>, a <p> and a link) drew
its heading, bold and larger. So: the tree builder, the cascade and
the layout were never at fault. The same trick cuts a large page down:
save it, delete half, look again.

4. Then compare with Chrome, rule by rule
-----------------------------------------
With the bytes known, read the page's own <style> and ask of each
declaration whether we honour it. On example.com's one rule that gave
the real differences, none of them about a heading:

- `background: light-dark(#eee, #222)`: the function was not known, the
  declaration dropped, the page white instead of grey. Fixed
  (Css_values.color).
- `min-height: 100vh`: a scrollbar on a page of five lines. The
  viewport's height was the constant 768 (Browser_page.viewport_height),
  not the window's, so 100vh was taller than the page's part of a window
  800 high. Fixed (the settings' height); and then a second cause
  showed, hidden by the first: a page exactly as high as its area still
  scrolled by a line, its lines rounded up and the area's down
  (Browser_tab.line_count).
- `display: grid; place-content: center`: laid out as a block, so the
  text is not centred down the window (the grid of history.md's list).
- `<script src=/s.js>`: not run (the host is not in default_allowed),
  and it is ES2015 (arrows, a spread, a /u regexp) for an ES5 engine.
  In Chrome it adds a picture above the text and five translations.

A dump with a scrollbar where Chrome has none, or a background of the
wrong colour, is worth the question "which declaration?" before "which
module?".

Lessons
-------
- A bug in a list is a claim: reproduce it, and read the page's
  source, before reading ours.
- Real sites change. A check against one (history.md's "example.com
  rendered pixel for pixel") is true of the day it was made; a page
  that must stay the same belongs in data/ or in a test's string.


Session 2 (2026-10-01): "a Wikipedia article is slow"
------------------------------------------------------

docs/history.md said the layout was slow, and proposed to measure
first. The network was suspected too (a TLS handshake per request).
Neither was it: the page's shapes are. No profiler was at hand (no
perf; ptrace_scope 1, so no gdb on a running program), and three
cheap measures were enough.

1. real against user: is it waiting, or computing?
--------------------------------------------------
  time ./bin/mini-chrome -dump-frame 400 /tmp/t.png url=... profile=off

  real 27.2 s   user 26.5 s

A program waiting for the network has a user time far under its real
time. Here they are the same: one core is busy from the first frame to
the last, and no faster network (gzip, keep-alive) would change much.

2. A time on each line of -v
----------------------------
-v says each request and each answer. A time before each line (a
filter of five lines of Python on stderr: time.time() - t0, then the
line; scripts/perf/load_timeline.sh, kept) shows the shape of the
load:

   0.04 GET  the page
   0.71 200  the page                     (the network: 0.7 s)
   1.56 GET  two sheets, four pictures    (read and laid out: 0.85 s)
   2.18 200  ...
   3.26 200  ... (four answers at once)
   5.90 200  ...
   7.19 200  ... (four at once)
   ...
  14.82 200  the last
  27.10 quitting                          (frame 400)

The answers come in bursts one to 2.6 s apart. Fetch.step hands the
answers at each Tick, so a burst is a frame, and a frame of 2 s is a
page laid out again once per answer in it: four answers, four times.

And the frames after the last answer: 600 frames take 33.6 s, 1200
take 51.8, so 30 ms of CPU a frame for a page nobody touches.

3. A harness that times the stages
----------------------------------
An executable linking the libraries (scripts/perf/Page_bench.ml, kept:
Http_client.get for the page and its sheets, then each stage between
two Unix.gettimeofday), on the same page:

  Charset, Html_lexer, Html_tree           12 + 33 + 28 ms
  Computed.styles (cascade, computed)     290 ms
  Box_layout.layout                        33 ms
  Browser_boxes.draw                      557 ms
  Browser_page.laid_out, styles memoized  520 ms
  the page over TLS, gzip                 457 ms (1246 the first time)

The layout is 33 ms. A relayout is 520 ms because of what follows it:
the shapes of every letter of a page 16,000 pixels high, a rectangle
for each segment of each stroke and a dot at each point (the round
pen), built though 713 pixels show. 24 answers, 24 times.

To time a stage that the module does not export (the cascade inside
lay_out), time the whole twice: once with a memo missed, once with it
hit; or rebuild its input with what is exported (Css_syntax.
parse_stylesheet and Computed.styles here).

Lessons
-------
- real = user: do not optimize the network.
- A name in a list of things to do ("the layout is slow") is a guess
  until each stage has its number: the layout was 6% of a relayout.
- Count how many times, not only how long: 0.5 s is slow, 24 times
  0.5 s is the 14 s.

What to do about it is docs/plan_performance.md. Its step 2 (the
shapes built when a line is shown) took a relayout from 450 ms to 28,
and the same two tools measured it, with opti=off for the "before" on
the same machine and the same day.


Session 3 (2026-10-02): "scrolling the Wikipedia article is sluggish"
----------------------------------------------------------------------

The letters had just become pictures, about:chrome scrolled smoothly
(a frame drawn in 8 ms instead of 74), and the article did not.

1. A script of the same gesture, against the same run at rest
-------------------------------------------------------------
-script presses keys at frames. 600 presses of the arrows after the
load ("down:500,down:502,...", then as many "up"), and the same run
without them, to the same frame: the difference of their CPU times
(/usr/bin/time's %U), divided by 600, is a scroll step. A page at
rest costs nothing now (the view's same list is not drawn), so the
difference is the steps alone.

With 150 presses the answer moved by 10 ms from one run to the next:
the load itself, with its TLS on threads, takes 5 to 7 s of CPU, and
that noise was divided by 150 only. With 600 it is steady to half a
millisecond. And a word added to the command line to label a run was
opened as a page: a third number that meant nothing. The two runs
must differ by the script alone.

2. The same measure on the other platform
-----------------------------------------
  Cairo:     pictures 340 ms a step, the pen's segments 145
  software:  pictures  52,           the pen's segments 197

Pictures slower than segments on one platform and four times faster
on the other: the fault is that platform's way with pictures, not
the pictures. Cairo's kept the last 32 it converted, and an article's
line has more different letters than that.

3. A clock round each part, in the real program, then taken out
---------------------------------------------------------------
The drawing alone was 7 ms (-uncapped at the scrolled place: every
frame drawn, the view the same list) and a step 26: 19 ms were not
the drawing. Page_bench had each suspect at 1.5 ms. So a table of
(count, total time) by name, a `timed "name" (fun () -> ...)` round
update by message, round view, and round four parts of the view,
printed at exit: Browser_media.draw 9.4 ms, controls_drawn 3.4,
animated 2.5 -- three readings of the page's 12,000 fragments, a
frame, for a page with no player. In the program they cost three
times what the bench said (the collector, with the rest of a frame's
work around). The clock was a throwaway: the files put back from
their copies, the numbers kept here.

Lessons
-------
- "Fast all the same" is a thing not understood: the cache of 32 was
  noted the day before as odd and left, because about:chrome was fast.
- A bench of one stage alone can be three times off the program's.
- Make the measure long enough that the run's own noise is small in
  it, and change one thing between two runs.
